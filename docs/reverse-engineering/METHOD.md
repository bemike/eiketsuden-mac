# 분석 방법론 (재사용 플레이북)

> **English summary** — A reusable playbook distilled from reverse-engineering the Korean DOS/V copy of
> *Sangokushi Eiketsuden*. Work outward from the cheapest, most certain layer: probe manifest → containers →
> palettes → graphics → maps → text → scenario bytecode → master tables. Use structural invariants
> (directory chains, exact decoded lengths, full input consumption, "every byte covered") as oracles; find
> tables inside the executable by byte-pattern search and confirm them by statically disassembling the x86-16
> code that reads them; follow loader code to resolve mappings the data alone
> cannot decide; render contact sheets and look at them; settle channel/plane order by experiment; check
> known answers from public walkthroughs. The page lists where the earlier research notes were wrong
> (absolute vs relative offsets, the little-endian `Ls11` spelling, the "10-bit map index" myth, the EUC-KR
> header assumption, a damaged file mistaken for a decoder bug), the synthetic-fixture + gated-golden-test
> pattern, emulator observation of a copy of the install in the official DOSBox-X (section 2.8, D22; static
> analysis only up to v0.2.1), and a checklist for applying all of this to another KOEI title of the same era.

이 문서는 영걸전 한국어 DOS/V판을 분석하면서 효과가 있었던 방법을, 같은 시기 KOEI 게임(공명전·조조전 등)에도 쓸 수
있게 순서와 기법으로 정리한 것입니다. 형식 자체는 [FORMATS.md](FORMATS.md), 원칙은 [README.md](README.md)에 있습니다.

## 1. 작업 순서

가장 싸고 확실한 층부터 바깥으로 넓힙니다. 앞 단계의 결과가 뒤 단계의 검증 도구가 됩니다.

| 단계 | 할 일 | 산출물 | 다음 단계에 주는 것 |
|---|---|---|---|
| 0. 프로브 | 파일 목록·크기·SHA-256·첫 16바이트를 매니페스트로 모음. 매직 넘버로 파일군을 가름 | `manifest.json` | 어느 파일이 어떤 컨테이너인지, 판본 |
| 1. 컨테이너 | LS11 같은 아카이브와 오프셋 표를 풀고 불변식을 모든 파일에 검사 | 항목 바이트 | 항목 크기 분포(그래픽 배치의 단서) |
| 2. 팔레트 | 실행 파일에서 팔레트 뱅크를 데이터 서명으로 찾고 채널 순서를 정함 | 색 | 그림을 눈으로 판정할 수 있게 됨 |
| 3. 그래픽 | 셀·플레인 배치, 항목 크기별 모양, 압축 이미지 코덱 | PNG, 컨택트 시트 | 맵 칩·유닛 그림 |
| 4. 맵 | 격자 배치, 칩 뱅크, 지형 층, 맵과 칩 세트의 대응 | 맵 JSON·PNG | 지형 코드, 좌표계 |
| 5. 텍스트 | 인코딩, 메시지 표, 문자열 경계 | 문자열 | 스크립트 피연산자 해석의 근거 |
| 6. 시나리오 | 바이트코드 구조, 트리거, 명령 집합과 피연산자 길이 | 해독된 스크립트 | 텍스트 경계 확정, 맵·그림 번호 대응 |
| 7. 마스터 표 | 무장·아이템·규칙 표의 배치 | JSON | 얼굴·병종·능력치 대응 |

텍스트(5)와 시나리오(6)는 서로를 검증합니다. 메시지 파일의 항목 경계는 바이트코드만 알고, 바이트코드의 명령 길이가
맞는지는 "메시지의 모든 바이트가 덮이는가"로 확인됩니다. 두 단계는 함께 진행하는 것이 빠릅니다.

## 2. 기법

### 2.1 구조 불변식을 오라클로

정답을 모를 때도 "틀렸다"는 알 수 있습니다. 가설마다 **실물 전체에 대해** 성립해야 하는 조건을 정하고, 하나라도 어기면
가설을 버립니다.

* **컨테이너**: 디렉터리 체인이 파일 끝에서 정확히 끝남, 복원 길이가 선언값과 같음, 입력을 완전히 소비함(채움 비트 제외).
* **개수 방정식**: 항목 수가 파일에 없으면 `N × 6 + Σ길이 = 파일 길이`처럼 유일한 해가 나오는 식을 세웁니다(6바이트 테이블).
* **길이 공식**: 맵 길이 `W×H×5/4 + 2`, 캠페인 맵 길이가 표의 크기 중 정확히 하나와 맞음.
* **완전 덮음**: 스크립트가 가리키는 대화·문자열이 메시지 섹션의 **모든 바이트**를 남김없이 덮음. 명령 길이가 하나만
  틀려도 이 조건이 깨지므로 명령 집합 전체의 검증이 됩니다.
* **범위**: 칩 번호가 뱅크 안, 지형 코드 < 20(예외 한 칸은 기록), 화자 번호 < 384, 배경 표 값 0–4.
* **교차 일치**: 메시지 섹션 수 = 장면 수, `IPPAN0` 조각 크기 = 실행 파일 표의 값, 네 장이 653개 문자열을 한 번씩 가리킴.

불변식을 통과하지 못하면 부분 결과를 쓰지 않고 정확한 오류로 실패시킵니다. 그래야 틀린 가설이 그럴듯한 출력 뒤에 숨지 않습니다.

### 2.2 바이트 패턴으로 표 찾기

실행 파일 안의 표는 두 가지로 찾습니다.

* **데이터 서명**: 표 자체의 모양. 예) 팔레트 뱅크 = 432바이트가 모두 ≤ 0x0F, 슬롯 5 = 슬롯 8, 바로 뒤 `80 40 20 10`.
  후보가 둘 이상이면 모호함으로 실패시킵니다.
* **코드 서명**: 표를 **읽는 명령어**의 바이트. 주소 자리를 와일드카드로 두고, 파일 전체에서 정확히 한 번(또는 예상한
  횟수) 나오는지 확인한 뒤 주소를 꺼냅니다. 예) `8A 5C 0C 2A FF 8A 87 _ _`(지형 → 배경 표). 표 값이 판본마다 달라도
  코드는 같을 가능성이 높아, 데이터 서명보다 다른 빌드에 강합니다.

두 방법 모두 **표를 저장소에 복사하지 않고** 사용자의 파일에서 읽게 해 줍니다. 서명 목록은 [FORMATS §15](FORMATS.md#main-exe).

### 2.3 x86-16 정적 역어셈블

* 도구: `ndisasm`, capstone 같은 16비트 역어셈블러와 직접 만든 파이썬 도우미(MZ 헤더 파싱, 이미지 오프셋 ↔ 파일 오프셋
  변환, DS 주소 해석, 바이트 패턴 검색, 문자열 참조 찾기).
* **주소 체계**를 먼저 정합니다: 파일 오프셋, 이미지 오프셋(파일 − MZ 헤더), DS 오프셋(데이터 세그먼트 기준). DGROUP은
  C 런타임 시작 코드의 `mov di, DGROUP`에서 읽습니다([FORMATS §15.1](FORMATS.md#main-exe)).
* **진입점 찾기**: 문자열(디버그 메시지, 파일 이름 `"FACEDAT.R3"` 등)의 DS 주소를 구해 그 주소를 참조하는 코드를
  찾습니다. 소프트웨어 인터럽트(`int 62h` 같은)는 유일한 호출 지점을 찾아 거꾸로 따라갑니다.
* **처리기 읽기**: 스크립트 인터프리터는 명령 분기(switch)에서 시작해 처리기마다 피연산자를 몇 바이트 읽는지(`READ8`,
  `READ16` 성격의 호출 횟수)를 셉니다. 처리기가 찍는 디버그 문자열(일본어 개발자 메시지가 남아 있음)은 이름의 좋은 단서입니다.
* **건너뛰기 표와 실행 경로를 둘 다 봅니다**: 인터프리터에는 명령을 실행하지 않고 건너뛸 때 쓰는 길이 표가 따로 있을 수
  있고, 그 표가 틀릴 수 있습니다(`0x1D`는 표에 2, 실제 4). 데이터 전체를 걸어 보는 검사(2.1)로 어느 쪽이 맞는지 가립니다.
* 드라이버(`TFDED.COM`)처럼 작은 COM 파일은 전체를 읽어 의사 코드로 옮기고, 파이썬 원형으로 실물 전체를 돌린 뒤 Rust로
  옮기고, 두 구현의 출력 해시를 비교합니다.

### 2.4 로더 코드를 따라가 대응 관계 풀기

데이터만으로는 정해지지 않는 대응은 **그 데이터를 읽는 코드**가 답을 갖고 있습니다.

* 맵 ↔ 칩 세트: 이음매 연속성으로 추측한 규칙은 도시 맵에서 틀렸습니다. 로더가 맵 번호를 `u16` 목록과 비교하는 루프를
  찾아 정답을 얻었습니다.
* `FACEDAT` 항목 수: 파일에 없지만 로더가 테이블 크기 상수(0x5A0)를 갖고 있습니다.
* 64 KiB를 넘는 메시지 기준: 메시지 읽기 함수가 넘친 두 기준에 0x10000을 더하는 코드를 갖고 있습니다.
* 팔레트 슬롯: 설정 루틴의 호출부를 따라가 슬롯이 상수 또는 데이터 레코드 값이라는 것(= 파일별로 고정이 아님)을 알았습니다.
* `BAKDATA` 구간: 로더가 읽는 네 길이가 그대로 레코드 표의 경계입니다.

### 2.5 컨택트 시트와 눈 검사

* 아카이브의 모든 항목을 한 장에(16개씩 한 줄) 그려 보면 배치 가설이 맞는지 한눈에 보입니다. 틀린 배치는 조각나거나
  줄무늬가 생깁니다.
* 슬롯별·채널 순서별 비교 시트, 지형 코드별 칸 모음(`percode`), 맵 위에 지형 코드·행군로 비트·보행 격자를 겹친 그림,
  무장 이름과 얼굴을 한 장에 그린 대조표가 특히 효과적이었습니다.
* 눈 검사는 "알아볼 수 있는 그림인가"를 판정할 뿐, 어느 팔레트 슬롯이 **게임에서** 쓰이는지 같은 것은 증명하지 못합니다.
  그런 것은 [추론]으로 남깁니다.

### 2.6 채널·플레인 순서 실험

* 색 채널: `[B][R][G]`·`[G][R][B]`·`[R][G][B]`·`[B][G][R]`로 같은 스프라이트를 그려 비교합니다. 피부·머리·칼날이
  자연스러운 것은 하나뿐이었습니다. 순수 원색 팔레트(슬롯 4의 1 = 파랑, 2 = 빨강, 4 = 초록)가 독립 근거가 되었습니다.
* 플레인 순서, 셀 순서(행 우선/열 우선), MSB/LSB, packed/planar도 같은 방법으로 가립니다.

### 2.7 공개 공략과의 대조(알려진 답)

플레이어 커뮤니티가 공개한 사실과 해독 결과를 대조합니다. 저장소에는 이런 확인용 수치만 들어갑니다.

* 능력치 순서: 조조 통솔 98·무력 75, 강유 지력 94, 제갈량 지력 100 같은 널리 알려진 값으로 통솔·무력·지력 순서를 정했습니다.
* 서장 흐름: 진유 막사에서 조조가 군자금 500을 줌, 사수관 30턴·화웅 격파 승리, 관우-화웅 일기토, 호로관 18턴에 여포 이동.
* 적장 병종·레벨(화웅 경기병 Lv5, 여포 Lv6), 그림 번호와 삽화 내용(동탁과 황제, 사냥터의 조조).
* 공개된 개수: 얼굴 240, `PACKGRP` 38, `HEXBCHR` 181, 전투 맵 59항목, 장면 1/5/4/5/3, 문자열 653.

이 값들은 `tests/golden.rs`의 `golden_korean_scenario_facts` 등에서 실물로 확인합니다.

### 2.8 에뮬레이터 관찰 (DOSBox-X, D22)

정적 분석으로 세운 가설을 원작의 실제 동작으로 확인하는 층입니다. 규칙은 [DECISIONS D22](../DECISIONS.md)를 따릅니다:
공식 빌드만 쓰고, 설치 폴더의 복사본에서 실행하며, 복제 방지는 우회하지 않고, 결과물은 로컬에만 둡니다.

**구성** (`res/`는 `.gitignore` 대상)

| 경로 | 내용 |
|---|---|
| `res/dosbox/app/bin/x64/Release/dosbox-x.exe` | DOSBox-X 2026.08.31 공식 포터블판(`dosbox-x-vsbuild-win64-…-portable.zip`, SHA-256은 `res/dosbox/zip.sha256`). 디버거 포함 빌드 |
| `res/dosbox/GAME` | 설치 폴더 복사본. 원작이 세이브를 여기에 씀 |
| `res/dosbox/dosbox-x.conf` | 원작 패키지 `dosbox.conf`와 같은 기계·소리 설정: `svga_s3`, 16 MB, `cycles=fixed 8000`, SB16 220/7/1/5, OPL auto. `[autoexec]`는 `mount c …GAME` → `HERO` |
| `res/dosbox/capture` | 에뮬레이터 캡처(스크린샷·OPL·WAV) |

실행: `dosbox-x.exe -conf res\dosbox\dosbox-x.conf -fastlaunch`.

**자동화**

- 창 캡처는 `PrintWindow`(`PW_RENDERFULLCONTENT`)로 합니다. 클라이언트 영역은 640×480이고, 창이 앞에 없어도 찍힙니다.
- **키 입력**
  - 창 메시지(`PostMessage`로 보내는 `WM_KEYDOWN`/`UP`)는 게임에 닿지 않습니다. SDL1 빌드에서 `SDL_VIDEODRIVER=windib`를 줘도 마찬가지입니다.
  - DOSBox-X의 **`AUTOTYPE`**(`autotype -w <대기 초> -p <간격 초> <키...>`)는 닿습니다. 이 명령은 `HERO` 앞에서 실행해 두면
    게임이 도는 동안 정해진 시각에 키를 넣습니다. 그래서 정해진 순서의 입력(예: 상태를 불러온 뒤 메뉴 이동)에 씁니다.
  - 대화형 입력이 필요하면 화면이 켜져 있을 때 데스크톱 자동화(computer-use)로 창을 직접 조작합니다.
- 보조 스크립트는 스크래치에 두고, 저장소에는 넣지 않습니다.

**확인 결과** (2026-10-01, 진행 중)

| 항목 | 결과 |
|---|---|
| 원작 기동 | 됨. `HERO.COM` → 복제 방지 코드 입력 화면("INPUT CODE" + 한자 세 글자 조합, 실행할 때마다 바뀜) |
| 창 캡처 | 됨(`PrintWindow`). 잠긴 화면에서는 확인 필요 |
| 키 입력 자동화 | `AUTOTYPE` 됨, 창 메시지 안 됨(위 "자동화") |
| 상태 저장·불러오기 | 확인 못 함(아래 BLOCKED) |
| 디버거(메모리 감시·덤프) | 확인 못 함(아래 BLOCKED) |
| OPL 출력 기록 | 확인 못 함(아래 BLOCKED) |
| 기존 세이브 `MSAVE1–4` | 확인 못 함(아래 BLOCKED) |

**BLOCKED (2026-10-01)**: 소유자의 사본에는 설명서·코드표가 없어, 복제 방지 코드에 답할 수 없습니다. D22에 따라 판정 코드를
해독하거나 우회하지 않으므로, 게임 본편의 관찰은 여기서 멈춥니다. 환경(`res/dosbox`)은 그대로 두며, 소유자가 정품 설명서를
갖게 되면 위 표의 남은 항목부터 이어 갑니다. 그때까지 관찰이 필요했던 일(ROADMAP M3·M5)은 정적 분석으로 진행합니다.

## 3. 함정과 조사 노트가 틀린 곳

앞선 조사 노트(다른 프로젝트의 공개 문서에서 모은 사실)는 출발점으로 유용했지만 여러 곳이 틀렸습니다. **노트의 주장은
가설로만 다루고 실물로 확인**해야 합니다.

| 노트의 주장 | 실제 | 어떻게 드러났나 | 교훈 |
|---|---|---|---|
| 6바이트 테이블 오프셋은 파일 기준 절대값 | **데이터 영역 기준 상대값**(0번 = 0) | 절대값으로 읽으면 첫 항목이 테이블 안을 가리킴; 로더의 `0x5A0 + 오프셋` | 오프셋의 기준점을 항상 확인 |
| LS11 디렉터리는 빅엔디언 | 매직이 `Ls11`(소문자)이면 **리틀엔디언** | 오프닝·엔딩 아카이브 3개만 디렉터리가 터무니없는 값 | 매직의 철자 차이도 의미가 있음 |
| 전투 맵은 10비트 타일 번호, 175 이상은 오버레이 | 칩 1바이트 + 2×2마다 지형 1바이트, 175 이상도 평범한 칩 | 5/4 길이의 정체가 지형 층; 칩 뱅크를 이어 붙이면 모든 값이 뱅크 안 | 길이 공식이 맞아도 해석은 틀릴 수 있음 |
| `DISK1.R3I`에 EUC-KR 헤더 `DOS/V 삼국지영걸전` | 한국어판도 **일본어 Shift-JIS 헤더** 그대로 | 실물 헤더 바이트 확인, 판본 식별이 `unknown`을 냄 | 현지화판은 원판의 흔적을 남김; 언어는 텍스트로 정함 |
| `OPGRP.R3` 디코딩 실패 = 디코더 버그 | **사본 자체가 손상**(0x60400부터) | 같은 코덱의 다른 22개 아카이브는 모두 통과; 손상 지점부터 바이트 통계가 급변 | 한 파일만 실패하면 파일을 의심하고 해시로 기록 |
| `SNRnM`은 NUL로 나뉜 문자열 목록 | 대화 레코드와 평문 문자열이 섞였고 경계는 바이트코드만 앎 | NUL 분할은 화자 번호의 0 바이트에서 쪼개짐 | 텍스트 파일도 구조가 있을 수 있음 |
| `SNRnM` 기준은 그대로 오프셋 | 16비트라 64 KiB에서 넘침 | 큰 파일의 기준이 앞 기준보다 작음 | 폭이 좁은 필드의 넘침을 의심 |
| `IPPAN0M`에 `u16` 색인 | 표 없는 문자열 모음, 색인은 `IPPAN0` | 색인으로 읽으면 텍스트가 깨짐 | 파일 이름이 비슷한 짝 파일을 확인 |
| 10바이트 레코드 = 유닛 슬롯, "이벤트 오프셋 표" | 트리거 레코드, 블록 표 | 인터프리터의 판정 함수 | 이름보다 읽는 코드를 믿기 |
| 명령 `0x18` = 합류 | `remove_person` | 처리기 동작과 데이터 문맥 | 이름은 처리기에서 확인 |
| `PACKGRP` = 16×16 공통 타일 | 화면 틀·삽화·로고 38장 | TF-DCE 헤더의 크기 | 용도 추정은 디코딩 후에 |
| `END.EXE` 장면 팔레트 16 × 48 | 43 × 48 + 2 | 블록 길이 측정 | 수치는 다시 잼 |
| 캠페인 맵 비트 = 육지 마스크(뜻 모름) | 0 = 행군로, 줄 사이 채움 없음 | 그림 위에 겹침 | 비트 층은 그려 보면 뜻이 보임 |

그 밖의 함정:

* **공개 해시와 비교할 수 없는 경우**: 다른 프로젝트가 공개한 "얼굴 0번 SHA-256 접두어"는 출력 배치가 문서화되지 않아 어떤
  배치로도 맞출 수 없었습니다. 해시는 무엇을 해시했는지 알 때만 쓸모가 있습니다.
* **모순된 건너뛰기 길이**(`0x19`): 실행 길이와 건너뛰기 길이가 다르고 데이터에 나오지 않는 명령은 추측하지 말고 거부합니다.
* **통계는 정답이 아님**: 칩별 지형 통계는 경계 칩에서 흔들립니다. 맵의 지형 격자처럼 게임이 실제로 읽는 값을 우선합니다.
* **눈 검사는 슬롯을 증명하지 못함**: 여러 슬롯이 다 그럴듯해 보일 수 있습니다(`PACKGRP` 16색 그림).

## 4. 합성 픽스처와 게이트 골든 테스트

원작 바이트 없이 CI를 돌리기 위해 두 층의 테스트를 둡니다.

1. **합성 픽스처(항상 실행)**: 우리가 만든 인코더·작성기(`ls11::build`, `table6::build`, `tfdce::fixture`, 플레인 인코더,
   팔레트 뱅크 작성기, `maps::build_exe_fixture`로 만든 최소 MZ 실행 파일, `text::build_messages`, `ippan::build`,
   `bakdata::build`)로 문서화한 형식대로 데이터를 만들어 왕복·손상 입력·불변식 위반을 검사합니다. `testutil.rs`는 이것들로
   **합성 설치본** 전체를 만들고, 텍스트는 지어낸 것입니다.
2. **골든 테스트(게이트)**: `EIKETSU_ORIGINAL_DIR`가 자기 설치본의 데이터 폴더를 가리킬 때만 실물로 돕니다.

   ```sh
   EIKETSU_ORIGINAL_DIR="D:/Games/영걸전/GAME" cargo test -p hero-import --test golden -- --nocapture
   EIKETSU_ORIGINAL_DIR="D:/Games/영걸전/GAME" cargo test -p hero-import --test tfdce_golden -- --nocapture
   ```

   * 주제별로 나눕니다(`golden_korean_ls11_archives`, `_table_containers`, `_map_geometry`, `_maps`, `_scenario_text`,
     `_scenario_facts`, `_palette`, `_sprites`, `golden_every_container_validates`, `golden_extraction_succeeds`).
     실패하면 어느 형식이 틀렸는지 이름으로 드러납니다.
   * **같은 검사를 합성 설치본에도** 돌립니다(`checks_pass_on_a_synthetic_known_answer_install`). 검사 코드 자체가 CI에서
     검증됩니다.
   * 손상된 사본 파일은 SHA-256·정확한 오류·정상 항목 수로 `KNOWN_DAMAGED`에 기록해, 한 파일의 실패가 나머지 검사를 가리지
     않게 합니다(해시는 사용자 파일의 지문이지 게임 내용이 아님).
   * 기댓값은 개수·크기·오프셋 같은 사실과 공개 공략 수치뿐입니다.

## 5. 다른 KOEI 게임에 적용하기 — 체크리스트

공명전·조조전·같은 시기의 DOS/V·PC-98 KOEI 게임에 적용할 때의 순서입니다.

**준비**

- [ ] 자기 정품인지, 설치 폴더를 읽기 전용으로 둘 곳(`.gitignore`된 로컬 경로)을 정했는지 확인
- [ ] 실행 원칙을 정함: 정적 분석만 할지, 공식 에뮬레이터로 관찰할지(이 프로젝트는 D22 이후 관찰을 함께 씀, 2.8절)
- [ ] 판본(언어·플랫폼·빌드)을 구분할 헤더·파일군 목록 작성

**컨테이너**

- [ ] 매직 넘버별 파일군 분류. `LS10/LS11/LS12`(대소문자 포함) 확인 — 철자별 바이트 순서 차이를 의심
- [ ] 디렉터리 체인·파일 끝 일치·정확한 복원 길이·완전 소비를 모든 파일에 검사, 실패 파일은 손상 여부부터 확인
- [ ] 머리말 없는 오프셋 표는 기준점(절대/데이터 영역)과 항목 수 방정식을 확인

**그래픽**

- [ ] 실행 파일에서 팔레트 뱅크를 데이터 서명으로 찾기(4비트 값 블록 + 뒤따르는 비트 마스크 바이트 등)
- [ ] 채널 순서 실험(영걸전은 `[B][R][G]`, 조조전도 B·R·G 순서라는 공개 자료가 있음)
- [ ] 항목 크기 분포로 셀 배치 가설(16×16 × 4 플레인 = 128 B의 배수?), 컨택트 시트로 확인
- [ ] packed planar와 플레인 순차 배치 둘 다 시험
- [ ] 압축 이미지는 드라이버/해제 루틴을 찾아 정적으로 읽기(`int` 호출 지점부터)

**맵**

- [ ] 길이 공식을 세우되 층(칩, 지형, 비트)을 분리해 해석
- [ ] 칩 뱅크 구성과 세트 선택은 로더 코드에서 확인
- [ ] 지형 이름 표(문자열 포인터 표)와 지형 → 배경 표로 코드 의미 교차 확인

**텍스트와 시나리오**

- [ ] 인코딩 통계(Shift-JIS/EUC-KR/Big5/GB)로 판정
- [ ] 메시지 표 폭 넘침 확인
- [ ] 인터프리터 switch, 처리기별 피연산자 길이, 디버그 문자열로 명령 집합 작성
- [ ] "모든 메시지 바이트가 덮임"과 "모든 바이트코드 바이트가 설명됨"을 동시에 만족시키기
- [ ] 트리거 레코드와 스크립트를 분리해 이해

**마스터 표와 규칙**

- [ ] 로더가 읽는 구간 길이로 레코드 경계 확인
- [ ] 공개 능력치로 필드 순서 확정
- [ ] 규칙 표는 공개된 다른 빌드의 오프셋을 참고하되 코드 서명으로 다시 찾기

**기록**

- [ ] 사실마다 신뢰도(검증/코드/추론/미상/외부) 표기
- [ ] 노트와 다른 점은 "정정"으로 남기기
- [ ] 합성 픽스처 인코더와 게이트 골든 테스트를 함께 만들기
- [ ] 데이터 값이 아니라 읽는 법만 문서화
